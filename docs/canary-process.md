# Canary-процесс релизов Remote Hub

Первый шаг staged rollout из `docs/release-playbook.md` (§7): между «CI собрал
релиз» и «автообновление раздаёт его всем» появляется пилотный контур.

## Как это работает

`release.yml` с 0.1.34 создаёт релиз **черновиком** (`draft: true`,
`make_latest: "false"`):

- electron-updater **не видит draft-релизы** — ни один пользователь ничего не
  получает автоматически;
- ассеты (`Remote.Hub.Setup.X.Y.Z.exe` + `latest.yml`) при этом уже лежат в
  draft — публикация меняет только видимость, ничего пересобирать не нужно;
- в step summary CI печатает дальнейшие шаги.

Дальше — ручной контур:

```
git tag vX.Y.Z && git push origin vX.Y.Z
  └─ CI: gates → build → DRAFT release (invisible to updater)
       └─ пилоты ставят exe вручную, чек-лист ниже
            └─ вердикт ОК → мейнтейнер:
                 node scripts/canary-publish.mjs --tag vX.Y.Z \
                   --notes .github/release-notes-vX.Y.Z.md --publish
                      └─ draft → published: апдейтер начинает раздачу
```

## Что делает canary-publish.mjs

1. Находит draft-релиз тега (`--tag vX.Y.Z`; без флага — версия package.json).
2. Проверяет ассеты: installer `.exe` + `latest.yml`.
3. Сверяет `version` и `sha512` из latest.yml с фактически скачанным exe
   (именно base64-дайджест, как считает electron-updater) — публикуемый
   бинарник гарантируемо тот, что описан в манифесте обновления.
4. `--notes <файл>` заменяет автосгенерированные notes на подготовленные.
5. Только с `--publish` публикует (`gh release edit --draft=false`). Без него —
   read-only верификация: можно прогонять сколько угодно раз до вердикта.

Всё через `gh` (`execFileSync`, без shell) — инъекции и случайные публикации
исключены.

## Чек-лист пилота

- [ ] Установить `Remote.Hub.Setup.X.Y.Z.exe` поверх рабочей версии
      (апгрейд, не чистая установка — путь миграции настроек тоже проверяем).
- [ ] Приложение стартовало, версия в «О программе» = X.Y.Z.
- [ ] Подключиться по RDP (IronRDP-движок) — экран рисуется, ввод работает.
- [ ] Подключиться по RDP (Legacy canvas) — кадры обновляются.
- [ ] Если доступен COM-host — встроенное окно открывается и закрывается чисто.
- [ ] VNC и SFTP сессии открываются.
- [ ] Закрыть вкладку сессии → процесс/мост умирает без «хвостов»
      (в диспетчере задач не остаётся rdp-com-host.exe / node-процессов).
- [ ] Выйти из приложения → нет зависших процессов; Credential Manager не
      содержит TERMSRV-записей после legacy-сессии (`cmdkey /list`).
- [ ] Обновление с X.Y.Z на следующий canary: апдейтер видит опубликованный
      релиз, ставит его, приложение перезапускается на новую версию.

## Роли

- **Мейнтейнер**: пушит тег, после зелёного CI раздаёт exe пилотам (готовое
  приглашение и шаблон отзыва — `docs/pilot-invitation.md`), собирает
  вердикты, выполняет публикацию скриптом (или через веб-интерфейс GitHub —
  кнопка «Publish release» на странице draft эквивалентна).
- **Пилоты**: ставят exe из draft, проходят чек-лист, докладывают вердикт
  (ОК / проблема с логами из «Журнал событий» → экспорт).

## Откат на canary-этапе

Пока релиз draft — отката не требуется: битую сборку просто удаляем
(`gh release delete vX.Y.Z --yes`) и пересобираем тег. Пользователям ничего
улететь не успело. Откат после публикации — см. `docs/release-playbook.md` §5.
