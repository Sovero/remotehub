# Architecture-Risk Report: три RDP-движка Remote Hub

**Дата:** 2026-09-04 · **Метод:** research-прогон паттерна 1 из `docs/swarm-patterns.md`
(рой `swarm-mtmi05ru`, strategy `research`). Живые headless-агенты не стартовали:
`claude` CLI не аутентифицирован на этой машине (нет OAuth-сессии, нет
`ANTHROPIC_API_KEY`) — исследование выполнено в текущей сессии по той же схеме
«исследователь на движок + аналитик», рой остаётся зарегистрированным для
повторного прогона после `claude /login` (см. §9).

**Периметр:** `src/main/rdp/` (iron-gateway 663 стр., manager 397, rdpjs-client 250,
com-launcher 184, iron-sessions 46), точки монтирования в `src/main/index.ts`
и `src/main/ipc.ts`, выбор движка в `src/renderer/src/store.ts`, версии из
`package.json`.

**Главный вывод:** архитектура «три движка = три независимых стека» оправдана
совместимостью (см. §2), но качество и жизненный цикл движков несопоставимы:
IronRDP — сопровождаемая внешняя зависимость, COM-host — тонкая обёртка над
системным mstscax.dll, а rdpjs — единственный движок, где весь RDP-стек
живёт в нашем main-процессе на мёртвой библиотеке. Приоритет инвестиций —
перевод rdpjs-сценариев на IronRDP (или удаление rdpjs как класса), а не
полировка трёх параллельных реализаций.

## 2. Карта движков

| | IronRDP (WASM) | Legacy canvas (rdpjs) | COM-host (MsTscAx) |
|---|---|---|---|
| Где исполняется | renderer: web-компонент `@devolutions/iron-remote-desktop` ^0.11.0 (WASM) | main: чистый JS `node-rdpjs-2` ^0.3.5 | отдельный процесс `rdp-com-host.exe` (C++, mstscax.dll) |
| Транспорт к UI | main — только мост: WS-сервер `127.0.0.1` (RDCleanPath, DER/ASN.1) → сырой пайп TCP; рендеринг в renderer | main → renderer: IPC `rdpjs:bitmap`, по одному сообщению на прямоугольник (BGRA32), рисует `RdpCanvas` | ничего не проходит через приложение: нативное owned-окно поверх контента вкладки (GWLP_HWNDPARENT), команды `hide/embed/setrect/show/focus/resize/quit` через stdin |
| TLS / NLA | rustls (WASM): TLS 1.2/1.3, CredSSP — строгая проверка Key Usage | собственный стек node-rdpjs-2 (X.224 → MCS → SEC): устаревший RDP-security/NLA | SChannel в mstscax.dll: CredSSP/NLA как у mstsc.exe |
| Пароль | renderer (store) | renderer (store) | `cmdkey /generic:TERMSRV/<host>` → Credential Manager; дополнительно пароль в stdin COM-хоста |
| Сильные стороны | единственный кроссплатформенный путь; поддерживаемая библиотека | нет нативных зависимостей; полный контроль из JS | единственный движок, который подключается к серверам с классическими сертификатами RSA key exchange (rustls не реализует RSA-обмен ключей ни в одной версии TLS — `manager.ts`, шапка); нативная производительность, resize, печать/буфер хоста |
| Слабые стороны | несовместим с «легаси»-сертификатами; мост — самописный протокольный код | мёртвая библиотека; весь протокол в нашем процессе; ввод только скан-коды/юникод; без буфера обмена | только Windows; E_ACCESSDENIED на ClearTextPassword обойдён через cmdkey (см. R2); окно — не WS_CHILD (DirectComposition Chromium), композитинг через координатную арифметику `embed.ts` |

**Почему именно три.** COM-host существует из-за неустранимого ограничения
rustls (RSA key exchange), rdpjs — как «чистый DOM»-вариант без HWND. Это
осознанное дублирование, а не случайность — но у него есть цена (R6).

## 3. Риски по движкам

### 3.1 IronRDP (WASM) — `iron-gateway.ts`, `iron-sessions.ts`

**R3 (средняя): самописный DER-кодек RDCleanPath.** В `iron-gateway.ts`
ручно реализованы TLV-кодирование/декодирование, сборка Request/Response/Error
PDU и минимальный разбор цепочки сертификатов. Код аккуратный (теги 0–9,
forward-совместимость «неизвестные поля игнорируем»), но это второй формат
проводного протокола в кодовой базе, который живёт только потому, что
web-компонент умеет подключаться исключительно через WS-прокси RDCleanPath.
Риск: расхождение с апстримом `ironrdp-rdcleanpath` при изменении версии
(константа `3390 = BASE_VERSION(3389) + 1` зашита). Митигируется тестами на
PDU (они есть) и тем, что формат стабилен уже в 0.11.x.

**R4 (средняя): «пробное» TLS-соединение.** Мост перед Response отдельным
TCP-соединением забирает цепочку сертификата сервера — иначе клиент не сможет
провалидировать её end-to-end. Это второе рукопожатие к тому же хосту: на
строгих шлюзах/RD Gateway с лимитом полуоткрытых соединений или при
round-robin-балансировке клиент может провалидировать сертификат одного
сервера, а туннель уйти на другой. Низкая вероятность (RDP-хосты обычно
одинаковые за балансировщиком), но при флейминге «не подключается к ферме»
проверять в первую очередь.

**R8 (низкая): WS-мост без токена.** `WebSocketServer({ host: '127.0.0.1' })` —
порт случайный и наружу не слушает, но любой локальный процесс пользователя
может просканировать loopback и подключиться к мосту. Данные через мост —
туннелированный RDP (свой TLS внутри), перехват — лишьDoS/искажение туннеля.
Дешёвый митигейт: одноразовый токен в пути WS (`wss://127.0.0.1/?t=...`),
проверка в `upgrade`.

### 3.2 Legacy canvas (rdpjs) — `rdpjs-client.ts`, `RdpCanvas.tsx`

**R1 (высокая): мёртвый стек в нашем процессе.** node-rdpjs-2 0.3.5 не
публикует релизов годами; его предшественник уже служил источником
критических CVE (prototype pollution и command injection в lodash-зависимости —
CHANGELOG 0.1.28). Вся реализация протокола (X.224/MCS/SEC, RLE через WASM
`rle.js`) исполняется в main-процессе Electron — привилегированном. Событие
`'error'` библиотеки не всегда завершает сокет, значит «застрявший» клиент —
реальный сценарий. Рекомендация: закрепить статус «совместимость, не развитие»,
добавить smoke-тест соединения к захваченному реплею (см. §5), и спланировать
вывод из эксплуатации после того, как iron закроет сценарий «старые серверы»
(например, опциональным послаблением проверки Key Usage в конфиге iron —
осознанный trade-off безопасности).

**R5 (средняя): транспорт битмапов через IPC.** Каждый прямоугольник кадра —
отдельное structured-clone сообщение `rdpjs:bitmap` с полным буфером пикселей.
На динамичном сеансе (видео, перетаскивание окон) это сотни сообщений в секунду;
до 0.1.29 поверх этого ходил ещё и stderr-спам библиотеки (устранено).
Остаточная стоимость: копия буфера на каждый кадр
(`data.buffer.slice(...)` в `index.ts`) + по putImageData на прямоугольник в
renderer (rAF-батчинг уже сливает очередь в один блит за кадр). Дальнейший
выигрыш возможен переносом RLE-распаковки и BGRA→RGBA в renderer/offscreen
или shared array buffer, но при жизненном цикле «депрекация rdpjs» (R1)
дальнейшая оптимизация не окупается.

**R7 (низкая): deprecated `Buffer.prototype.slice`.** В горячем пути
`index.ts:367` используется `bitmap.data.buffer.slice(...)`, создающий копию
и помеченный deprecated в новых Node. Замена на
`Buffer.from(bitmap.data.buffer, bitmap.data.byteOffset, bitmap.data.byteLength)`
— механическая, без изменения поведения (тот же clone для structured clone).

### 3.3 COM-host — `manager.ts`, `com-launcher.ts`, `embed.ts`

**R2 (высокая): работа с паролем.** Композит из двух обоснованных, но
чувствительных решений: (а) `cmdkey /generic:TERMSRV/<host>` пишет пароль ОС в
Credential Manager пользователя — там он переживёт сессию приложения, если
процесс упал до cleanup (`/delete:` вызывается только из `cleanup()` и при
`stop()`); (б) пароль дублируется в stdin COM-хоста первой строкой — он не
попадает в argv (верно!), но виден любому процессу, который откроет пайп
stdin, и хранится в дампе памяти main-процесса как JS-строка. Кромка: при
`killChild`/краше COM-хоста запись cmdkey остаётся. Митиге́йты по возрастанию
эффекта: cleanup-запись cmdkey по `before-quit` для всех живых сессий;
`/delete:` в `closeAll()`; среднесрочно — DPAPI-шифрование в Credential
Manager не существует, но можно перейти на `CredWrite` с областью видимости
сессии и гарантированным удалением через `finally`.

**Специфика встраивания.** Окно COM-хоста — owned (не WS_CHILD) из-за
DirectComposition-композитинга Chromium; координация идёт через текстовые
команды stdin + `SetWindowPos` в физических пикселях (конверсия DIP→px
разнесена между `ipc.ts` и `index.ts:407`). Это тонкое место при изменении
масштабирования/мультимонитора — любые правки слоёв координат требуют
e2e-прогона (см. §5). Debounce resize 300 мс уже стоит — хорошо.

## 4. Дублирование и точки унификации

1. **Три источника правды о «сессии RDP».** iron живёт в renderer
   (web-компонент + событие `iron-reconnect-*`), rdpjs — в карте
   `RdpjsClientManager.sessions`, COM-host — в `RdpManager.active` с собственным
   сторожем. Жизненные циклы не симметричны: у rdpjs нет сторожа и таймаутов
   соединения, у COM-host есть debounce/kill-grace, у iron — таймауты в
   `IronGateway`. Унификация: единый интерфейс `RdpEngine`
   (connect/disconnect/input + события состояния) в `src/shared` — контракт
   IPC уже почти им является (`ipc-contract.ts`).
2. **Двойной ввод координат.** `RdpCanvas` и `LegacyRdpView` по-своему
   конвертируют CSS-px → координаты протокола. Общая утилита в `src/shared`
   уберёт класс рассинхронизаций при HiDPI.
3. **Секреты.** Пароль для iron/rdpjs берётся из renderer-store, для COM-host —
   через `resolveAuth` в main. Одна точка (main) для всех трёх устранила бы
   нахождение plaintext-пароля в renderer-памяти — заодно закроет и часть R2.
4. **Таймауты.** `IronGateway` параметризует все таймауты (хорошо), rdpjs не
   имеет ни одного таймаута соединения (Promise может остаться незавершённым
   при молчащем сервере) — 1:1 перенос схемы таймаутов iron в rdpjs, если
   движок остаётся.

## 5. Тестовое покрытие и пробелы

- **Есть:** unit на PDU/DER (`tests/iron-gateway*.test.ts`), на нормализатор
  битмапов и конфиг rdpjs (`tests/rdpjs-client.test.ts`, 7 тестов, добавлены
  0.1.29), инъекция зависимостей в `RdpManager` (watchdog/killGrace для тестов),
  всего 144 теста, typecheck зелёный.
- **Пробел 1:** интеграционного теста «TCP-сервер, притворяющийся RDP-хостом,
  отвечает заранее записанным X.224/TLS-сценарием» нет ни для iron-моста, ни
  для rdpjs — регрессии формата кадров (как баг 0.1.29) и всплытия TLS-кода
  ловятся только на живом хосте.
- **Пробел 2:** нет теста на cleanup cmdkey при аварийном завершении (R2).
- **Пробел 3:** нет e2e на координатную арифметику embed (DIP↔физ. пиксели) —
  риск R-раздела 3.3. Рекомендуется запись реплея сценария в
  `npm run test:e2e:rdp` при наличии живого хоста.

## 6. Рекомендации (по приоритету)

1. **Быстро (< день):** заменить deprecated `slice` в `index.ts` (R7);
   одноразовый токен на ws-мосте (R8); cleanup cmdkey в `closeAll()`/`before-quit`
   (R2). — **Выполнено 2026-09-04 (0.1.30):** R7 — точная копия кадра в
   `index.ts`; R8 — токен сессии проверяется при ws-upgrade (`?token=`) и в
   proxy_auth Request PDU, выдаётся через `IronStartResult.authToken`;
   R2 — `purgeCmdkeyCredential` в `closeAll()` (единый формат ключа —
   `cmdkeyTargetFor`), тесты `tests/quick-fixes.test.ts`.
2. **Ближний спринт:** скелет `RdpEngine`-интерфейса + перенос таймаутов в
   rdpjs (§4.1, §4.4); integration-replay тесты (§5).
3. **Стратегически:** план вывода rdpjs из эксплуатации (R1) — принят
   (`docs/rdpjs-deprecation-plan.md`, фазы до 0.2.0). Исследование показало:
   валидация сертификата в WASM-клиенте уже ослаблена де-факто, а реальный
   блокер — отсутствие RSA key exchange в rustls — закрывается не «релаксацией»,
   а детекцией несовместимости (`incompatible-server-cert`) с авто-фоллбэком
   на legacy; опциональный upstream-трек описан в §3.4 плана.

## 7. Что уже хорошо

- Разделение «main = транспорт, renderer = рендеринг» выдержано во всех трёх
  движках; iron даже не пропускает пиксели через main (туннель WS↔TCP).
- Пароль не в argv COM-хоста (корректное осознание Win32_Process.CommandLine).
- Debounce resize, kill-grace, сторож перевстраивания окна — продуманные
  детали COM-host.
- Таймауты и silence-detection в `IronGateway`; forward-совместимый разбор
  PDU («неизвестные поля игнорируем»).
- После 0.1.29 rdpjs нормализует мусорные кадры вместо падения — класс багов
  «экран замер» закрыт.

## 9. Воспроизведение свармом (кросс-чек)

Рой `swarm-mtmi05ru` зарегистрирован в claude-flow (координационная оболочка).
Живой кросс-чек R1–R8 выполняется харнессом `scripts/crosscheck-swarm.mjs`:
4 headless-агента (`claude -p`; iron / rdpjs / comhost / analyst), инструменты
ограничены Read/Glob/Grep/Write, исходники защищены (контроль `git status`
в конце прогона), вердикты классифицируются как CONFIRMED-OPEN /
CONFIRMED-FIXED-SINCE / REFUTED / NEW-RISK.

```bash
claude /login                          # одноразово, интерактивно
node scripts/crosscheck-swarm.mjs      # вердикты: .claude-flow/research/crosscheck/
```

После прогона свести вердикты в приложение к этому отчёту (§10) и обновить
статусы R1–R8; REFUTED-вердикты требуют file:line-доказательства — без них не
принимаются. Отчёт — контрольная точка: задача сворма не «написать доку», а
независимо подтвердить/опровергнуть R1–R8 и найти пропущенное.
