# Спека: устранение находок аудита Remote Hub

Глубина: **deep** (полная проработка каждого измерения по каждому требованию,
явное «не применимо» там, где измерение не относится к делу). Режим: **full**
— решения по неоднозначным пунктам приняты агентом и помечены `ASSUMPTION`,
без вопросов пользователю.

## Задача

Remote Hub — рабочее production-приложение (v0.1.14, зелёный CI/CD), но
предыдущий аудит нашёл пять конкретных технических долгов: реальную
security-дыру в SSH (никто не проверяет, с тем ли сервером говорит
пользователь), мёртвый код на 1500+ строк и нативный бинарник, которые никто
не может вызвать из интерфейса, точку входа приложения на 2125 строк, где
90% — не относящийся к делу тестовый код, забытую правку конфигурации сборки,
которая ничего не делает, и журнал событий, который не даёт быстро найти
нужную запись среди сотен разных подключений. Пользователь поручил закрыть
всё это одним заходом, без дальнейших вопросов.

## Решение

После этого захода: SSH-подключение к незнакомому серверу спрашивает
подтверждение отпечатка (и громко предупреждает, если отпечаток сервера
внезапно изменился); из кодовой базы и из инсталлятора исчезает нерабочий
ActiveX-путь; `main/index.ts` содержит только запуск приложения и укладывается
в лимит проекта; конфигурация сборки не содержит мёртвого кода; в окне «Лог»
можно искать текст, фильтровать по источнику события и экспортировать журнал
в файл, а окно не тормозит при тысячах записей.

## Решения по реализации

### §1 — SSH host key verification (R01)

- Новый модуль `src/main/sessions/host-keys.ts`: `HostKeyStore` поверх
  существующего `Store` (по аналогии с тем, как `CredentialsFile` хранится
  сегодня) — новый файл `hostkeys.json` в `userData`, формат
  `{ schemaVersion, entries: { "<host>:<port>": { algo, fingerprint,
  firstSeenAt } } }`. Отдельный файл, а не расширение `ProfilesFile`/
  `SettingsFile` — отпечатки не относятся к профилям хостов и не должны
  участвовать в их экспорте/импорте.
- `ssh2` даёт хук `hostVerifier(keyHash, callback)` — синхронный callback,
  а решение пользователя асинхронное (модальный диалог в renderer). Поэтому
  `SshSession.open()` при первом получении ключа переводит сессию в то же
  состояние, что уже используется для keyboard-interactive —
  `{ phase: 'auth-required', detail: 'host-key:<new|changed>:<host>:<port>:<algo>:<fingerprint>' }`
  — и держит `hostVerifier`-callback в замыкании до ответа через новый метод
  `SshSession.resolveHostKey(accept: boolean)`.
  IPC-канал переиспользуется тот же (`session:auth`/`sessionAuth`), но его
  payload расширяется: сегодня `SessionAuthRequest`/`preload.sessionAuth`
  принимают только пароль строкой — это не годится для да/нет решения по
  ключу. `SessionAuthRequest` становится объединением
  `{ sessionId, password: string } | { sessionId, hostKeyDecision: 'accept' | 'reject' }`,
  а `ipc.ts`-обработчик разбирает форму запроса и вызывает либо
  keyboard-interactive `finish`, либо `resolveHostKey` — один канал для
  обеих форм «ответа на auth-required», без нового IPC-имени.
- **ASSUMPTION** (решение вместо вопроса пользователю, т.к. это дело
  вкуса/архитектуры, не бизнес-факт): TOFU (trust-on-first-use), как в
  OpenSSH — не «библиотека доверенных CA», это соответствует масштабу
  приложения (одиночный desktop-клиент, не флот серверов).
- Смена ключа детектируется сравнением алгоритма+отпечатка с сохранённой
  записью. UI обязан визуально отличать «новый хост» от «хост сменил ключ»
  (второе — красный акцент, текст explicitly называет прошлый и новый
  отпечаток), см. §1 «Boundaries» ниже.
- `rdpAutoAcceptCert` (настройка для RDP-сертификатов) не имеет отношения к
  SSH host key — не переиспользуется и не путается с ним даже по названию.

**Depth pass — R01:**

| Измерение | Решение |
|---|---|
| First run | нет `hostkeys.json` → создаётся лениво при первом принятии; до первого SSH-подключения файла не существует — это нормально, не ошибка |
| Empty | пусто = «нет ни одного известного хоста» — не отображается пользователю нигде отдельно, это внутреннее состояние |
| Wrong input | пользователь нажимает «Отклонить» → `resolveHostKey(false)`, сессия переходит в `error` с текстом «Отпечаток сервера не подтверждён — соединение отменено», запись в журнал (`ssh`, warn) |
| Failure | сеть падает во время ожидания решения пользователя → `ssh2` сам разорвёт соединение (`client.on('close')`), диалог в renderer закрывается по приходу `state: 'closed'|'error'` для этого sessionId |
| Interruption | пользователь закрывает вкладку сессии, пока диалог подтверждения ещё открыт → `SshSession.dispose()` вызывается как обычно; отложенный `hostVerifier`-callback не вызывается (не нужно — ssh2 сам считает соединение оборванным), утечки нет, т.к. callback хранится в замыкании конкретного `SshSession`, которое уходит в GC вместе с объектом |
| Growth | сотни известных хостов → одна плоская Map по ключу `host:port`, O(1) чтение/запись, размер файла линейный — не проблема даже на тысячах записей |
| Boundaries | смена ключа — самый важный случай: отдельный, более настойчивый диалог («Сервер изменил идентификацию!» + старый/новый отпечаток), кнопка принятия НЕ дефолтная (в отличие от обычного первого TOFU, где кнопка «Подключиться» может быть основной) |
| Aftermath | принятый отпечаток пишется в `hostkeys.json` немедленно после подтверждения (до того, как сессия перейдёт в `connected`) — запись в журнал уровня `info` для нового хоста, `warn` для смены ключа |

### §2 — Удаление COM-хоста / MsRdpClient9 (R02)

**ASSUMPTION-1** (принято за пользователя — это инженерное решение, не
продуктовое; альтернатива «оставить как явный fallback-engine» отклонена):
путь удаляется целиком, а не переводится в третий вариант `RdpEngine`. Три
причины: (а) исходное ТЗ прямо перечисляет отказ от mstsc/MsTscAx/COM как
цель проекта, а не только как «не по умолчанию»; (б) держать 1500+ строк и
нативный C++/COM-бинарник ради пути, которым никто не может воспользоваться
(нет пункта в настройках, нет ветки в `store.ts`), — чистые расходы на
поддержку и площадь атаки без выгоды; (в) IronRDP (по умолчанию) и rdpjs
(легаси JS) уже дают ровно тот функциональный охват, который был у
COM-пути, без ActiveX.

Удаляются целиком:
- `src/main/rdp/manager.ts`, `com-launcher.ts`, `win32-engine.ts`,
  `embed.ts`, `launcher.ts`, `generator.ts` (все — использовались только
  `RdpManager`, не переиспользуются `iron-gateway.ts`/`rdpjs-client.ts`);
- `src/native/` целиком (`rdp-com-host.cpp`, `binding.gyp`,
  скомпилированные артефакты — `.exe` был закоммичен для `extraResources`);
- `scripts/build-com-host.cmd`;
- запись `extraResources` в `package.json` (`rdp-com-host.exe`);
- IPC-каналы, существующие только ради этого пути:
  `rdpLaunch/rdpExited/rdpCertificate/rdpCertificateAccept/
  rdpCertificateReject/rdpRect/rdpActivate/rdpOverlay` — и их обработчики в
  `ipc.ts`, и объявления в `ipc-contract.ts`, и методы в `preload/index.ts`
  и `preload/index.d.ts`;
- ветки `RH_SMOKE_RDP_EMBED` и `RH_SMOKE_RDP` в `src/main/index.ts` (тестируют
  именно этот путь — `mstsc`/embedding, а не iron/rdpjs);
- тесты `tests/rdp.test.ts`, `tests/rdp-embed.test.ts`,
  `tests/rdp-com-host.test.ts` (последний — незакоммиченный, добавлен уже
  после того, как путь стал мёртвым).

Не трогается: `RdpEngine` продолжает быть `'iron' | 'rdpjs'` (уже так в
`shared/types.ts` — никаких изменений типа не требуется), `.rdp-pane`/
`.rdp-pane--embedded` CSS-класс и `RdpPane` в `App.tsx` (общая обёртка для
iron/rdpjs, к COM-пути отношения не имеет — проверено чтением кода), тесты
`rdp-iron-e2e.test.ts`, `iron-gateway.test.ts`, `iron-probe.test.ts`.

**Depth pass — R02** (техническая уборка, большинство измерений
объективно не применимо к пользователю приложения — явно помечено):

| Измерение | Решение |
|---|---|
| First run / Empty / Wrong input / Interruption / Boundaries | не применимо — путь никогда не был виден пользователю, поведения UI не меняется |
| Failure | риск — что-то ссылается на удаляемые модули и сборка ломается; приёмка — `npm run typecheck && npx vitest run && npm run build` зелёные после удаления |
| Growth | обратный эффект: минус нативный бинарник + минус ~1500 строк — размер `app.asar`/инсталлятора уменьшается |
| Aftermath | `CHANGELOG.md`/следующий релиз получает строку «убран неиспользуемый ActiveX-путь RDP» (см. §6 «Швы для тестов» — CHANGELOG не редактируется этим заходом автоматически, т.к. версия ещё не бампится; строка добавляется как часть коммита, а не отдельного релиза) |

### §3 — Разгрузка `main/index.ts` (R03)

Новая структура:
- `src/main/index.ts` — только: single-instance lock, `app.whenReady`,
  создание окна, регистрация меню и IPC, `before-quit` — то, что там и было
  до 2125 строк.
- `src/main/smoke/index.ts` — единая точка `installSmokeHooks(mainWindow,
  store, rdp/rdpjs/vnc/...)`, вызываемая из `index.ts` одной строкой внутри
  `app.whenReady`, если хотя бы одна `RH_SMOKE_*` переменная выставлена;
  ничего не делает в обычном (production) запуске.
- `src/main/smoke/ui-flows.ts`, `smoke/rdp-flows.ts`, `smoke/vnc-sftp.ts`,
  `smoke/contrast.ts`, `smoke/capture-help.ts` — группировка по смыслу
  существующих веток (`RH_SMOKE_ICONS`/`RH_SMOKE_UPDATE`/`RH_SMOKE_CONTRAST`
  → ui-flows/contrast; `RH_SMOKE_RDP_IRON`/`RH_SMOKE_RDP_RESOLUTION` →
  rdp-flows; `RH_SMOKE_VNC`/`RH_SMOKE_VNC_ERROR`/`RH_SMOKE_SFTP` →
  vnc-sftp; `RH_CAPTURE_HELP` → capture-help), каждый модуль < 500 строк.
  Ветки `RH_SMOKE_RDP_EMBED`/`RH_SMOKE_RDP` не переносятся — удаляются
  вместе с §2.
- Перенос **дословный** (копирование тела веток без переписывания логики) —
  это чистое перемещение кода, не переписывание тестов: риск регрессии
  создаёт именно переписывание, а не перенос.

**Depth pass — R03:**

| Измерение | Решение |
|---|---|
| First run / Empty / Wrong input / Interruption / Boundaries | не применимо — внутренний рефакторинг, не user-facing |
| Failure | главный риск переноса — случайно изменить поведение одного из ~15 сценариев; приёмка — построчное сравнение перенесённого тела веток с оригиналом (diff, а не пересказ), плюс прогон тех сценариев, что не требуют реального RDP/VNC-хоста (`RH_SMOKE=1` базовый, `RH_SMOKE_ICONS=1`) |
| Growth | новые модули не растут вместе — у каждого своя тема, добавление нового `RH_SMOKE_*` в будущем идёт в соответствующий по теме файл, а не обратно в `index.ts` |
| Aftermath | `main/index.ts` — единственный источник правды о том, что происходит на старте приложения; ссылка на smoke-модуль — одна строка, легко удалить целиком, если когда-то понадобится вырезать все smoke-тесты из продакшен-бандла |

### §5 — LogDialog (R05.1–R05.5)

- Фильтр по источнику и поиск — состояние компонента (`useState`), как уже
  сделано для `levelFilter` — не персистентно между открытиями диалога,
  консистентно с текущим поведением.
- Список источников для фильтра строится из `Array.from(new
  Set(entries.map(e => e.source)))`, не из фиксированного списка — если
  появится новый `LogSource`, фильтр не потребует правки.
- Экспорт в файл — новый IPC-канал `logs:export` (main: `dialog.showSaveDialog`
  + `fs.writeFileSync`), потому что `showSaveDialog` — Node/Electron API,
  недоступный в renderer напрямую (не открываем `nodeIntegration`). Формат
  файла — тот же построчный текст, что и у «Копировать», плюс заголовок с
  датой экспорта и версией приложения (уже доступна через `app:info`).
- «Скопировать диагностику» — целиком в renderer (нет нового IPC): берёт
  `window.api.getAppInfo()` (уже существует), `settings` из стора (без
  секретов — `Settings` и так их не содержит) и последние 500 записей из
  **полного** `entries` (не из отфильтрованного/усечённого списка).
- Рендер-лимит — `filtered.slice(-300)` плюс строка-баннер, если
  `filtered.length > 300`. 300 — обоснованный дефолт (виден весь экран
  прокруткой за разумное время, не даёт заметной просадки рендера), не
  настраивается пользователем — это техническая мера, не продуктовая
  настройка.

**Depth pass — R05.1 (фильтр по источнику):**

| Измерение | Решение |
|---|---|
| First run | журнал пуст → селектор источников показывает только «Все источники» (список пуст, деградирует красиво) |
| Empty | после выбора источника, для которого сейчас 0 записей (перекрыто ещё и `levelFilter`/поиском) → специфичный empty state: «Нет записей источника «vnc» с текущими фильтрами» + кнопка «Сбросить фильтры» |
| Wrong input | не применимо (select, не текстовый ввод) |
| Failure / Interruption | не применимо |
| Growth | `Set` + `filter` на буфере ≤2000 — без задержки на глаз |
| Boundaries | не применимо |
| Aftermath | выбор источника не сохраняется между открытиями диалога (см. решение выше) |

**Depth pass — R05.2 (поиск):**

| Измерение | Решение |
|---|---|
| Wrong input | пустая строка = без фильтра; спецсимволы regexp не интерпретируются — поиск по `includes()`, не по `RegExp`, чтобы `(`, `[` и т.д. в тексте ошибки не ломали поиск |
| Empty | 0 совпадений → «Ничего не найдено по «<запрос>»» + «Сбросить поиск» (тот же компонент empty state, что и R05.1, с параметром) |
| Interruption | закрытие диалога сбрасывает поле поиска (не персистентно, как и `levelFilter` сегодня) |
| Growth | комбинация уровень+источник+текст — три последовательных `.filter()`, всё ещё O(n) на 2000 записей, не требует индексации |

**Depth pass — R05.3 (экспорт в файл):**

| Измерение | Решение |
|---|---|
| Wrong input | не применимо (нет текстового ввода, только диалог сохранения файла) |
| Failure | пользователь отменил `showSaveDialog` → тихо ничего (не ошибка); запись на диск не удалась → toast с русским текстом «Не удалось сохранить журнал: <причина без внутренних путей>» |
| Interruption | не применимо — операция синхронная и короткая |
| Growth | экспортируется весь **отфильтрованный** список (не только видимые 300 из R05.5) — иначе экспорт «для поддержки» окажется обрезанным |
| Boundaries | путь сохранения выбирает пользователь через системный диалог, инициированный явным кликом — не тайная запись на диск |
| Aftermath | после успешного сохранения — toast с именем файла, событие не дублируется в сам журнал (иначе журнал бы бесконечно логировал собственный экспорт) |

**Depth pass — R05.4 (кнопка «Скопировать диагностику»):**

| Измерение | Решение |
|---|---|
| Failure | тот же паттерн `try/catch` + toast, что у существующего `copyAll` |
| Growth | 500 записей — фиксированный, не растущий с общим объёмом буфера предел именно для диагностики (баланс между полнотой и объёмом текста, который реально можно вставить в переписку/тикет) |
| Aftermath | результат — один текстовый блок: шапка (версия/Electron/arch/платформа), краткий дамп нечувствительных настроек, затем записи журнала — пригоден для вставки как есть в багрепорт |

**Depth pass — R05.5 (лимит рендера):**

| Измерение | Решение |
|---|---|
| Growth | это и есть содержание требования — от него зависит, тормозит ли диалог на большом журнале |
| Aftermath | лимит рендера не влияет на «Копировать»/«Экспорт»/«Диагностику» — они всегда берут полные (или намеренно расширенные для R05.4) данные, ограничивается только DOM |
