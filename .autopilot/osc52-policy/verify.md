# Живая проверка OSC 52

Дата: 17.11.2026. Хост: Windows, Docker Desktop (перед проверкой был выключен,
после — снова остановлен).

## Стенд

- Контейнер `alpine:3.20` с OpenSSH 9.7p1 и tmux 3.4, проброс `127.0.0.1:2222 → 22`,
  вход root по сгенерированному ed25519-ключу.
- Клиент — `ssh2` с pty `TERM=xterm-256color` (это и есть «терминал», которому tmux
  шлёт OSC 52). tmux: `set-clipboard on`, `allow-passthrough on`, `history-limit 5000`.
- Байты сервера подавались в настоящие `parseOsc52` / `osc52Action` / `utf8Length`
  из `src/shared/osc52.ts` (собран esbuild'ом). Сами последовательности из потока
  вырезались сканером `ESC]52;…BEL|ST`: xterm.js в Node не грузится (нужен DOM),
  поэтому его внутренняя диспетчеризация OSC в этой проверке не участвовала.

## Что реально прошло

| Сценарий | Что пришло по SSH | Результат |
|---|---|---|
| Копирование в copy-mode tmux (`set-clipboard on`) | `ESC]52;;T1NDNTItTElWRS1CT0RZLTQy BEL` | `parseOsc52` → `OSC52-LIVE-BODY-42`; тот же текст оказался в буфере Windows |
| OSC 52 от программы внутри tmux, UTF-8 | `ESC]52;c;<base64> BEL` | декодировано `Привет-OSC52-ЮНИКОД`, 31 байт, кириллица в буфере не побилась |
| Текст больше предела: 120 000 байт | одна последовательность, base64 на 160 002 символа | `osc52Action('allow', 100000, …)` → `too-large`; при `0` (без предела) → `copy`; размер 117.2 КБ |
| Политики на живом тексте | — | `ask` → `ask`, `allow` → `copy`, `deny` → `ignore`; `ask` при 120 КБ → `too-large` (предел срабатывает до вопроса) |
| Нативный буфер Windows | — | запись/чтение через PowerShell — совпало; Electron main `clipboard.writeText/readText` — совпало, кириллица целая |

## Находки

**Пустое поле selection.** tmux отправляет `ESC]52;;<base64>` — selection пустой,
а не `c`. `parseOsc52` трактует пустой selection как системный буфер; если бы код
требовал явный `c`, копирование из tmux не работало бы вообще. Поведение закреплено
тестом: `parseOsc52(';…')` возвращает текст.

**terminfo и `set-clipboard`.** Первый прогон не дал ни одной последовательности, и
причина оказалась в стенде: мы выставили
`terminal-overrides "xterm*:Ms=\E]52;%p1%s;%p2%s\007"`, tmux съел `\E`, и в поток
ушло `E]52;;…` без ESC — мусор. Без оверрайда tmux 3.4 сообщает `clipboard` в
`#{client_termfeatures}` для `xterm-256color` и шлёт правильный `ESC]52;…`.
Практический вывод: OSC 52 доходит только если terminfo клиента знает
`Ms`/`clipboard`; на стороне приложения это не лечится, но при жалобах
«tmux не копирует» проверять нужно именно возможности терминала.

## Что осталось непроверенным

- **Модалка `ask`**: её показ и клики «Скопировать / Не копировать» — нужен живой
  Electron-окно, автоматизации UI для него в проекте нет (jsdom не установлен).
  Покрыто иначе: тест `tests/osc52-ask.test.ts` проверяет, что `ask` заполняет
  данные модалки (текст, размер, предпросмотр) и не пишет в буфер.
- **Тост при превышении предела** и мгновенное применение смены политики к уже
  открытой вкладке — это состояние React в окне.
- **Полная цепочка renderer → IPC `clipboard:write-text` → main** в запущенном
  приложении: main-процессный clipboard проверен отдельно, сам IPC-вызов — нет.
